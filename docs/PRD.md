# Spendly 제품 요구사항

기준일: 2026-10-20. 요구사항 원본: [PROJECT_SPEC](PROJECT_SPEC.md). 이 문서는 원본의 제품 범위를 정리한 파생 문서이며 구현 완료를 의미하지 않는다.

## 목표와 일정
개인의 수입·지출, 월 예산, 정기결제 예정일을 관리하는 모바일 우선 웹 서비스다. 1인 개발, 주 15~20시간, 6주(90~120시간) 동안 프런트엔드·백엔드·인증·DB·테스트·배포 전 과정을 경험한다.

## 범위
| 우선순위 | 요구사항 |
| --- | --- |
| P0 | 가입·로그인·로그아웃, 거래 CRUD, 카테고리, 월 예산, 대시보드, 거래 검색·필터 |
| P1 | 정기결제 등록·수정·일시정지, 예정 결제, 월별 통계, 반응형, 테스트·배포 |
| P2 | CSV 내보내기 |

제외: 금융기관 연동, OCR, AI 분석, 네이티브 앱, 다중 통화, 공동 가계부.

## 핵심 규칙
- 거래 금액은 양의 정수 원화이며 수입·지출은 type으로 구분한다. 환불은 수입으로 기록한다.
- 예산은 사용자·월당 하나이며 소비 합계에는 지출만 포함한다.
- 거래 카테고리는 동일 사용자 소유이고 유형이 일치해야 한다. 거래가 있는 카테고리는 보관 처리한다.
- 구독은 예정 정보만 저장한다. 실제 거래를 자동 생성하지 않아 이중 집계를 막는다.
- PAUSED 구독은 예정 결제에서 제외한다. 해당 월에 billing_day가 없으면 마지막 날로 보정한다.
- 모든 소유 리소스에 인증 사용자 기준 접근을 적용한다. 거래 수정 충돌은 version으로 감지한다.
- 날짜는 초기 Asia/Seoul의 사용자 로컬 날짜이며 DB 발생일은 DATE다.

## 완료 기준
신규 가입자가 실제 배포 URL에서 거래를 기록하고 예산·구독 예정일을 조회할 수 있어야 한다. 다른 사용자의 데이터 접근이 차단되고 핵심 E2E와 서버 테스트가 통과해야 한다. 포트폴리오는 시연 계정과 가짜 데이터로 공개한다.

## 남은 세부 결정
기술·원화·UUID·세션 인증은 원본에 명시되어 있다. 페이지 기본값과 정렬 문법, 필드 길이, 집계 응답 구조, CSRF 토큰 전달 방식, 정확한 SameSite 값·배포 구성 등 원본에 없는 세부 사항은 구현 전 확인한다. 현재 차이는 [아키텍처](ARCHITECTURE.md), 일정은 [로드맵](ROADMAP.md)을 따른다.

## 사용자 설계 갱신 (2026-10-20)
첫 마이그레이션을 위해 PROJECT_SPEC의 users 물리 설계를 사용자 승인으로 확정했다. 이메일은 앞뒤 공백 제거·소문자 통일 후 저장하며 최대 254자다. 인증·사용자 기능은 미구현이다. 제품 범위와 주차별 순서는 변경하지 않았다.

## 카테고리 설계 갱신 (2026-10-20)
사용자 승인에 따라 이름은 최대 50자, 앞뒤 공백 제거·빈 이름 금지·대소문자 구분으로 확정했다. 같은 사용자·유형·이름의 중복은 보관 상태와 관계없이 금지한다. 신규 카테고리는 보관하지 않은 상태로 시작한다. DELETE는 보관 처리하며, 보관 카테고리의 신규 거래 선택·복원 정책은 미확정이다. PROJECT_SPEC과 DB 설계에 물리 제약을 반영했으며 API 구현 완료를 의미하지 않는다.

## 거래 설계 갱신 (2026-10-20 사용자 승인)
PROJECT_SPEC에 거래 물리 설계를 확정했다. 거래 설명은 필수·빈 내용 금지·최대 100자, 메모는 선택·최대 1000자이며 미입력은 빈 문자열로 저장한다. 금액은 1~999999999999999원의 정수다. 보관 카테고리는 새 거래·카테고리 변경 시 선택할 수 없고, 기존 연결을 유지하는 금액·메모 수정은 허용한다. 복원 정책은 미확정이다. updated_at·version은 향후 JPA로 관리한다. SQL 작성과 업무 기능 구현 완료는 구분한다.

## JPA 매핑 구현 (2026-10-20)
사용자 승인에 따라 User·Category·Transaction 엔티티와 TransactionType enum을 작성했다. 금액 BigDecimal, 발생일 LocalDate, 시각 Instant, 앱 UUID 생성과 거래 @Version을 매핑했다. 도메인 규칙 자체는 변경하지 않았다. API·입력 검증·정규화·비밀번호 해시·사용자 격리·보관 정책은 여전히 미구현이다.

## 인증 구현 순서 변경 (2026-10-20)
사용자 승인으로 실제 인증 사용자 ID를 거래 서비스에 연결하기 위해 원래 3주 차 인증을 거래 서비스·HTTP API보다 먼저 구현한다. 제품 범위는 유지한다. 세부 계약은 [인증 설계 초안](AUTH_DESIGN.md)에서 확인 대기이며 아직 구현하지 않았다.

## 인증 구현 갱신 (2026-10-20)
사용자 승인으로 AUTH_DESIGN 세부 정책을 PROJECT_SPEC에 확정 반영하고 가입·로그인·로그아웃·현재 사용자·CSRF 조회를 구현했다. 가입 후 자동 로그인하지 않고, 비밀번호 12~128자·PBKDF2 해시, 세션 30분·HttpOnly/Lax·운영 Secure, CSRF와 로그인 제한을 적용한다. 회원 정보 응답은 id·email만 포함한다. 단일 서버 메모리 제한이며 배포 검증은 남아 있다. 거래 서비스·API는 여전히 미구현이다. 실행 가이드는 AUTH_GUIDE를 따른다.

## 카테고리 API 구현 갱신 (2026-10-20 사용자 승인)
PROJECT_SPEC의 카테고리 계약을 확정했다. 기본 목록은 보관 제외, includeArchived=true로 보관을 포함한다. 이름만 수정하고 생성 후 유형 변경은 금지한다. 보관 반복 요청은 204, 중복 이름은 409, 타인/미존재 항목은 동일 404로 처리한다. 보관된 카테고리 이름 수정은 허용하며 복원은 미확정·범위 밖이다. 서비스·API·입력 검증·인증 ID 연결을 구현하고 임시 PostgreSQL 전체 32개 테스트·임시 서버 실제 HTTP 검증을 완료했다. 근거는 ROADMAP을 따른다.

## 카테고리 정렬 변경 (2026-10-20)
사용자 요청에 따라 목록을 생성 시각순에서 이름 오름차순·동일 이름 ID 오름차순으로 변경했다. 기본·보관 포함 목록 모두 적용한다. 한글 가나다순·동명 ID 순서·보관 필터·사용자 격리 관련 테스트를 통과했다.
