# Spendly 제품 요구사항

기준일: 2026-10-20. 요구사항 원본: [PROJECT_SPEC](PROJECT_SPEC.md). 이 문서는 원본의 제품 범위를 정리한 파생 문서이며 구현 완료를 의미하지 않는다.

## 목표와 일정
개인의 수입·지출, 월 예산, 정기결제 예정일을 관리하는 모바일 우선 웹 서비스다. 1인 개발, 주 15~20시간, 6주(90~120시간) 동안 프런트엔드·백엔드·인증·DB·테스트·배포 전 과정을 경험한다.

## 범위
| 우선순위 | 요구사항 |
| --- | --- |
| P0 | 가입·로그인·로그아웃, 거래 CRUD, 카테고리, 월 예산, 대시보드, 거래 검색·필터 |
| P1 | 정기결제 등록·수정·일시정지, 예정 결제, 월별 통계, 반응형, 테스트·배포 |
| P2 | CSV 내보내기 |

제외: 금융기관 연동, OCR, AI 분석, 네이티브 앱, 다중 통화, 공동 가계부.

## 화면
| 경로 | 내용 |

| `/dashboard` | 당월 수입·지출·잔액, 예산 진행률, 최근 거래, 예정 결제 |

| `/analytics` | 월별·카테고리별 집계 |
| `/settings` | 월 예산·카테고리 관리·계정 |

## 핵심 규칙
- 거래 금액은 양의 정수 원화이며 수입·지출은 type으로 구분한다. 환불은 수입으로 기록한다.
- 예산은 사용자·월당 하나이며 소비 합계에는 지출만 포함한다.
- 거래 카테고리는 동일 사용자 소유이고 유형이 일치해야 한다. 거래가 있는 카테고리는 보관 처리한다.
- 구독은 예정 정보만 저장한다. 실제 거래를 자동 생성하지 않아 이중 집계를 막는다.
- PAUSED 구독은 예정 결제에서 제외한다. 해당 월에 billing_day가 없으면 마지막 날로 보정한다.
- 모든 소유 리소스에 인증 사용자 기준 접근을 적용한다. 거래 수정 충돌은 version으로 감지한다.
- 날짜는 초기 Asia/Seoul의 사용자 로컬 날짜이며 DB 발생일은 DATE다.

## 완료 기준
신규 가입자가 실제 배포 URL에서 거래를 기록하고 예산·구독 예정일을 조회할 수 있어야 한다. 다른 사용자의 데이터 접근이 차단되고 핵심 E2E와 서버 테스트가 통과해야 한다. 포트폴리오는 시연 계정과 가짜 데이터로 공개한다.

## 남은 세부 결정
기술·원화·UUID·세션 인증은 원본에 명시되어 있다. 페이지 기본값과 정렬 문법, 필드 길이, 집계 응답 구조, CSRF 토큰 전달 방식, 정확한 SameSite 값·배포 구성 등 원본에 없는 세부 사항은 구현 전 확인한다. 현재 차이는 [아키텍처](ARCHITECTURE.md), 일정은 [로드맵](ROADMAP.md)을 따른다.

## 사용자 설계 갱신 (2026-10-20)
첫 마이그레이션을 위해 PROJECT_SPEC의 users 물리 설계를 사용자 승인으로 확정했다. 이메일은 앞뒤 공백 제거·소문자 통일 후 저장하며 최대 254자다. 인증·사용자 기능은 미구현이다. 제품 범위와 주차별 순서는 변경하지 않았다.

## 카테고리 설계 갱신 (2026-10-20)
사용자 승인에 따라 이름은 최대 50자, 앞뒤 공백 제거·빈 이름 금지·대소문자 구분으로 확정했다. 같은 사용자·유형·이름의 중복은 보관 상태와 관계없이 금지한다. 신규 카테고리는 보관하지 않은 상태로 시작한다. DELETE는 보관 처리하며, 보관 카테고리의 신규 거래 선택·복원 정책은 미확정이다. PROJECT_SPEC과 DB 설계에 물리 제약을 반영했으며 API 구현 완료를 의미하지 않는다.
